# 设计规范：Windows 原生 Session 健康检测与修复系统

## 0. AI 使用说明

- 本文档定义产品的界面结构、视觉系统、组件、状态和交互规则。
- `Product-Spec.md` 是功能范围的事实来源；本文档不得新增 Product Spec 没有定义的核心功能。
- 本产品是界面型内部运维后台，填写界面型章节；终端 / 对话式 Agent 章节为 N/A。
- AI MUST 优先设计 P0 flows 和 P0 screens。
- AI MUST 覆盖默认、加载、空、错误、成功等关键状态。
- AI MUST 保持页面、组件、交互和视觉 tokens 的一致性。

## 1. 设计方向

### 1.0 产品形态

| 维度 | 方向 |
|---|---|
| 形态 | 界面型 |
| 本体 | 页面与组件 |
| 落地分轨 | 使用 §2 信息架构、§3 页面规格、§5 视觉系统、§8.3 响应式 |

### 1.1 设计目标

把一个原本分散、靠经验和脚本拼出来的运维流程，收敛成一个可快速判断状态、可直接执行动作、可追踪根因的内部操作台。设计目标不是“好看”，而是“判断快、误操作少、失败时能迅速定位”。

### 1.2 产品气质

| 维度 | 方向 |
|---|---|
| 语气 | 专业、直接、克制 |
| 信息密度 | 紧凑 |
| 视觉风格 | 工具型 Dashboard / 运维后台 |
| 情绪目标 | 让用户感到可控、可靠、明确，不花哨、不混乱 |

### 1.3 设计原则

- DP-001: 状态优先。用户第一眼先看到“现在什么是好的、什么坏了、下一步该做什么”。
- DP-002: 操作贴近结果。能执行的动作必须出现在相关数据旁边，不让用户来回跳页找按钮。
- DP-003: 工具感强于装饰感。所有颜色、间距、圆角、动效都服务于识别和操作，不做情绪化设计。
- DP-004: 风险场景必须高压可见。`RISK`、锁定、失败这些状态必须比普通成功更显眼。
- DP-005: 前端只解释当前动作，不替后端掩盖复杂度。比如 profile 实际路径、运行位置、风险类型都应明确显示。

### 1.4 参考与反参考

**正向参考：**

| 参考产品 | 具体喜欢哪一点（拆成属性） | 必须保留 |
|---|---|---|
| Linear | 高密度但不乱；筛选、列表、状态色很克制 | Yes |
| GitHub | 工具界面的分层、灰阶控制、危险操作表达明确 | Yes |
| Grafana | 面向排障的 Dashboard 结构，先看状态再看细节 | Yes |
| Vercel Dashboard | 顶部操作清晰、页面说明简短、信息组织直接 | No |

**反参考：**
- Notion：留白太松，适合内容编辑，不适合高频运维操作。
- Airtable 新手态：信息层级容易平均化，风险和成功的差别不够尖锐。
- 消费级 CRM SaaS：圆润、热闹、营销感太强，会稀释工具的可信度。

> 这套界面不是给人逛的，是给人排障和执行的。别做成“温柔好用”的假象，要做成“冷静好用”的工具。

## 2. 信息架构

### 2.1 导航结构

固定左侧导航 + 右侧主内容工作区。左侧承担一级导航，不折叠成顶部；右侧顶部统一承担页面标题、页面说明、全局快捷操作。

### 2.2 页面清单

| 页面编号 | 页面名称 | 页面目的 | 关联流程 / 需求 | 优先级 |
|---|---|---|---|---|
| SCREEN-001 | 健康检测任务 | 配置检测、调度、失败修复并执行 | FLOW-001, FLOW-002 / REQ-001 | P0 |
| SCREEN-002 | 脚本库 | 管理脚本资源与元信息 | FLOW-001 / REQ-004 | P0 |
| SCREEN-003 | 目录库 | 管理浏览器 Profile 和锁状态 | FLOW-001 / REQ-003 | P0 |
| SCREEN-004 | 脚本运行 | 追踪脚本执行实例并控制 | FLOW-001, FLOW-002 / REQ-002 | P0 |
| SCREEN-005 | 运行日志 | 检索关键动作和故障线索 | FLOW-002 / REQ-006 | P0 |
| SCREEN-006 | 环境自检 | 查看节点环境可用性 | FLOW-003 / REQ-005 | P0 |
| SCREEN-007 | 部署配置 | 解释部署路径、启动方式和环境约束 | FLOW-003 / REQ-006 | P0 |

### 2.3 页面关系

- 健康检测任务是系统核心页与默认落点，任务失败时在脚本运行与运行日志中留下可追踪记录。
- 脚本库、目录库、健康检测任务相互关联，构成日常配置路径。
- 脚本运行页是执行监控路径，展示所有 ScriptRun 实例的实时状态与控制。
- 环境自检、部署配置、运行日志是辅助排障路径。
- 所有详情查看优先用弹窗，不拆成新的详情页。

## 3. 页面规格

### SCREEN-001: 健康检测任务

**页面目的：**  
系统核心页：配置检测规则、调度与失败修复，并手动触发检测/修复。

**主要操作：**  
新增健康检测、编辑、立即检测、执行修复脚本、查看日志、启停、克隆、删除。

**次要操作：**  
- 查看执行时间线
- 搜索任务

**布局结构：**
1. 顶部区域：页面标题、说明、全局快捷操作按钮组。
2. 工具栏：搜索框 + 状态筛选。
3. 主内容区：健康检测任务表格。
4. 编辑弹窗：三 Tab（检测配置 / 高级调度 / 失败修复）。
5. 执行时间线弹窗：展示该任务的检测与修复记录。

**内容层级：**

| 优先级 | 元素 | 说明 |
|---|---|---|
| 1 | 检测状态与最近结果 | 先判断当前是否有效 |
| 2 | 检测目标与失败修复 | 明确范围和处置方式 |
| 3 | 调度信息 | cron、最近/下次执行时间 |

**使用的组件：**

| 组件编号 | 组件名称 | 用途 |
|---|---|---|
| CMP-001 | 顶部操作按钮组 | 承载全局高频操作 |
| CMP-005 | 紧凑数据表格 | 展示检测任务 |
| CMP-007 | 行内操作按钮组 | 检测/修复/编辑/启停 |
| CMP-010 | 配置表单弹窗（三 Tab） | 新增或编辑检测任务 |
| CMP-009 | JSON 文本区域 | 编辑请求头/请求体/规则/脚本配置 |

**必需状态：**
- 默认：展示任务列表与状态。
- 加载：表格骨架屏。
- 空状态：无任务时显示说明和“新增健康检测”按钮。
- 错误：检测失败、修复失败、目录锁冲突时明确提示。
- 成功：保存、检测、修复成功有 toast，状态刷新。
- 禁用 / 权限受限：停用任务灰化；`RISK` 状态单独高亮并标注已发提醒。

**响应式表现：**
- 移动端：表格横向滚动；编辑弹窗全屏化。
- 平板端：压缩辅助列。
- 桌面端：完整表格 + 三 Tab 弹窗。

**可访问性说明：**
- 状态标签必须有文本，不只靠颜色。
- JSON 文本区域支持键盘输入。

**响应式表现：**

**可访问性说明：**

## 4. 组件规格

### CMP-001: 顶部操作按钮组

**组件用途：**  
承载页面或系统级主动作。

**使用位置：**  
SCREEN-001, SCREEN-002, SCREEN-003, SCREEN-006

**变体：**

| 变体 | 用途 |
|---|---|
| Primary | 当前页面最重要动作 |
| Secondary | 普通辅助动作 |
| Danger | 重置、关闭、清空等危险动作 |

**状态：**

| 状态 | 视觉表现 | 交互表现 |
|---|---|---|
| 默认 | 实心或描边按钮，12px 圆角 | 可点击 |
| 悬停 | 阴影微增，边框/底色更明确 | 鼠标提示可操作 |
| 聚焦 | 2px 外发光焦点环 | 键盘可见 |
| 激活 | 颜色略深 | 按下反馈 |
| 禁用 | 透明度 50%，光标禁用 | 不响应点击 |
| 加载 | 左侧 spinner，不改按钮尺寸 | 禁止重复点击 |
| 错误 | Danger 按钮保留红色语义 | 可配错误提示 |

**内容规则：**
- 主按钮使用动词开头，如“执行环境自检”“上传脚本”“新增健康检测”。
- 危险按钮必须明确结果，如“取消执行”“删除任务”，禁止写“确认”。

**可访问性要求：**
- 所有按钮最小点击区域 36px 高。
- 焦点态必须明显。

## 6. 交互与反馈规则

### 6.1 全局交互规则

| 模式 | 规则 |
|---|---|
| 主操作 | 放在页面右上或弹窗右下，使用 Primary 按钮 |
| 次要操作 | 使用描边按钮，放在主操作左侧或工具栏中 |
| 危险操作 | 使用 Danger 按钮，必要时二次确认 |
| 保存行为 | 手动保存，不做自动保存 |
| 导航 | 一级页面靠左侧导航切换；详情通过弹窗，不拆新路由 |
| 弹窗 / 抽屉 | 当前版优先使用居中弹窗，不用右侧抽屉 |

### 6.2 反馈规则

| 场景 | UI 反馈 | 文案规则 |
|---|---|---|
| 成功 | 右下角 toast + 列表即时刷新 | 直接说结果，如“Profile 已登记” |
| 错误 | toast 或字段错误 + 局部错误条 | 直接说原因，不写“请求异常”这种废话 |
| 警告 | 橙色标签或 callout | 说明风险但不夸大 |
| 空状态 | 卡片或表格空占位 + 下一步按钮 | 说明现在没有什么，并告诉用户该干嘛 |
| 加载 | 骨架屏、loading 按钮、逐项刷新 | 文案简短，如“执行中”“检测中” |

### 6.3 动效规则

- 只允许功能性动效，不做装饰性动效。
- 允许按钮 hover、弹窗出现、自检项状态切换、toast 出入场。
- 禁止大面积位移动画、夸张缩放、长时间渐变。
- 动效时长统一控制在 `120ms ~ 180ms`。

## 7. UX 文案与内容规则

### 7.1 文案语气

清晰、直接、专业。像内部运维工具，不像客服，不卖萌，不安慰。

### 7.2 按钮文案规则

- 主按钮使用动词 + 对象，如“执行环境自检”“上传脚本”“保存任务”。
- 次按钮用明确动作，如“关闭”“查看全部”“详情”。
- 危险按钮必须说明后果，如“取消执行”“删除任务”。

### 7.3 表单文案规则

- label 使用字段本身或业务名词，不绕。
- placeholder 用格式提示，不写空话。
- helper text 用来解释路径规则、运行位置、上传目录等技术约束。
- error message 直接指出错因，如“Profile Key 不能为空”“不是合法 JSON”“路径不能跳出 RUNTIME_ROOT”。

### 7.4 空状态文案规则

- 空状态要解释现在为什么是空。
- 必须给下一步动作。
- 不使用鼓励式废话，如“快来创建吧”；改用“暂无健康检测任务，先新增一条检测任务配置”。

## 8. 可访问性与响应式要求

### 8.1 可访问性目标

基础可访问性，达到内部工具可用标准，接近 WCAG 2.2 AA。

### 8.2 必需可访问性规则

- [x] 所有可交互元素可通过键盘访问
- [x] 焦点状态清晰可见
- [x] 表单字段有明确 label
- [x] 错误信息与对应字段关联
- [x] 不只依赖颜色表达状态
- [x] 正文和背景有足够对比度
- [x] 图片和图标有合适的替代文本或被标记为装饰性
- [x] 页面标题和区块标题结构清晰

### 8.3 响应式规则

| 断点 / 设备 | 规则 |
|---|---|
| 移动端 `< 768px` | 左侧导航折叠；顶部操作按钮换行；表格保持横向滚动；弹窗全屏或近全屏 |
| 平板端 `768px - 1023px` | 统计卡片 2 列；双栏内容改上下堆叠；表单保留 2 列但允许必要时单列 |
| 桌面端 `>= 1024px` | 固定左侧导航；顶部操作右对齐；保持完整表格与双栏信息布局 |

## 9. 实现说明

- 前端实现建议沿用 `Vue 3 + TypeScript + Vite + Pinia + Axios + Element Plus`。
- 如果使用组件库，优先把组件库当基础骨架，再用 CSS Variables 收紧主题，不直接使用默认皮肤。
- 必须定义全局 design tokens：颜色、圆角、阴影、字体、间距、状态色。
- 当前不要求暗色模式。别一上来做主题切换，先把浅色主方案做稳。
- 必须保留等宽字体用于路径、脚本目录、JSON、日志和技术字段。
- 避免使用过度圆润、渐变重、营销感强的组件样式。
